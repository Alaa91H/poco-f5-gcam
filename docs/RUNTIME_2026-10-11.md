## Earlier controlled evidence (2026-10-11)

Pixel Camera's factory requested PRIVATE 800x600/max11/usage2816,
RAW10 4624x3472/max30/usage259 and YUV 800x600/max52/usage259.
With the exact sizes and usages, the probe failed session configuration.
Changing YUV usage alone from 259 to 3 allowed configuration. The APK applies
that fallback only to YUV_420_888 with usage259; RAW and PRIVATE remain unchanged.

The modified Pixel Camera now configures its photo graph but still receives
capture failures from frame0 and PRIVATE buffer loss. The configuration fix is
therefore insufficient to make photography work.

Camera2 Probe delivered 12 YUV frames with RAW and PRIVATE frames using the
same graph. Controlled comparisons also succeeded with faceDetectMode128,
FACE_PRIORITY/controlMode2, the Pixel crop, lens shading map enabled, and the
PRIVATE/YUV/RAW stream order. These values were not patched speculatively.
The same-signed probe temporarily installed under the exact GoogleCamera package
also delivered frames. The Pixel Camera APK was restored with `install -r`,
preserving app data; its exact version was verified afterward.

Video mode requests four outputs: preview1920x1080, JPEG4624x2600,
YUV1280x720 and encoder1920x1080. CameraDeviceClient rejects this graph as an
unsupported input/output combination. The observed rejection is evidence;
it does not prove that merely deleting a stream would preserve Pixel video.

Some EVA/Graph-URO errors also occur during successful probe shutdown. Those
messages alone are not treated as a root-cause diagnosis. The remaining Pixel
photo request/buffer failure has not been isolated to a verified repair.

## Follow-up: enumeration and sustained RAW capture

The Java graph selected camera4 while the existing open-device adapter opened
camera0. A controlled enumeration candidate excludes aliases3/4/5/6 before Java
camera selection, matching the native metadata adapter. The helper is in a fifth
DEX because the original DEX is at its method-reference limit. Four generated
DEX filter cases executed successfully on the phone; 107 Python tests passed.

Installed enumeration APK SHA256:
`00fd51942bbba0fca3633af0e4ee5c509299847ddc9408bdb90fa7aa63a696b8`.
The new trace confirms CameraGraph0 and CameraDevice0. Real photo preview became
visible and the shutter enabled, but preview repeatedly stops after a short
interval. An actual shutter attempt did not produce a new camera image.

Sustained Camera2 tests supersede the earlier 12-frame evidence: the exact
PRIVATE/RAW10/YUV graph stops after61 frames with cameraError4. The HAL reports
`Raw_Out_RealTime_0: Max number of nodes reached64`, followed by Raw_Callback
configuration failure and a serious camera-device error. The independent probe
closes acquired images immediately, so this failure does not require Pixel's
image retention. RAW16, RAW CPU usage3, face detection0, three client-name
variants, RawCbSourceType0/1 and EnableIdealRAW1 reproduce the failure. These
experimental vendor parameters were not added to the Pixel APK.

PRIVATE+YUV delivered120 frames. Keeping RAW configured but excluding it from
repeating preview requests also delivered120 YUV frames, with zero RAW frames.
That validates an isolation experiment, not Pixel HDR+ photography; removing
RAW targets alone would leave Pixel's RAW capture processing without its input.

The camera4 probe did not produce a fresh report and left a connection pending;
its saved `long-id4` report is stale and invalid for camera4. Camera2 errors2
during that interval are not evidence against RAW16 or the other stream graphs.
RAW16 and no-RAW comparisons were rerun after the connection released.

A separate `camcorder.trk_yuv=false` APK was installed and tested. It still
requested the four-output graph and failed recording; it is rejected. Turning
off video stabilization through the app's settings also failed recording.
No video file was saved. The unverified tracking patch was removed from the
workspace. The enumeration candidate was restored successfully with install-r;
video stabilization was restored to its original enabled value and verified in
the UI. The final strict report `20261011-pixel-enumeration-restored.json`
confirms startup/session configuration but fails pipeline compatibility (exit1).

## 2026-10-12 controlled video-session comparison

The independent probe now supports separate YUV dimensions, JPEG outputs,
PRIVATE encoder-surrogate buffers, and a configuration-only real HEVC encoder
surface. With PRIVATE 1920x1080, YUV 1280x720, JPEG 4624x2600 and encoder
1920x1080, the four-output session configures when clientName is unset.
Removing JPEG/YUV or reducing JPEG also configures, so output count alone is
not an established cause of the Pixel failure.

With identical stream order and parameters, setting
`com.xiaomi.sessionparams.clientName=com.android.camera` changes the result to
`onConfigureFailed`. The real `c2.qti.hevc.encoder` comparison reproduced
success/failure/success for unset/stock-client/unset. Evidence:
`20261012-video-graph-real-default.json`, `real-stock-client.json`, and
`real-default-repeat.json` (same filename prefix). These are session-configuration
results, not saved-video proof. The subsequent Pixel recording test is reported
below.

Photo request-template comparisons (ZSL, still, preview with still intent,
record) all configured but failed at 61 frames with cameraError4. Changing the
request template does not resolve sustained RAW delivery.

## 2026-10-12 OpenCL photo crash guard (experimental)

A temporary in-process signal recorder located the MergeThread null call at
libgcastartup offset 0x6e08eb4. The wrapper calls a null
clGetImageRequirementsInfoEXT pointer. An ARM64 guard returns
CL_INVALID_OPERATION (-59) when that pointer is absent. The on-device ABI
harness verified both branches: `missing=-59 present=1234567 calls=1`, including
all nine arguments in the supported branch. GCam then logs its existing
single-base-frame SpatialMerge fallback. This does not enable multi-frame HDR.

The clean candidate starts from the no-client APK and contains no fault recorder:
`pixel-camera-11.0-opencl-guard-clean.apk`, SHA256
`b0cdc2a57bbb4d46b9062825f495ccff725a6722dbb8cd93d5fa0988036fc9a5`.
APK v3 signature and 16 KiB native-library alignment checks passed. It was
installed successfully on the same POCO F5 and tested:

- Photo: finalized `PXL_20261012_122921534.jpg`, 722,584 bytes, decoded RGB
  1728x2304 with nonzero channel variation. This proves one quick shutter
  capture using the fallback, not repeated captures after prolonged preview.
- Video: finalized `PXL_20261012_123025991.mp4`, 51,193,968 bytes; 541 frames,
  approximately 30.07 fps / 17.99 seconds. Beginning, middle and ending frames
  decoded with nonzero variation. Audio quality and other modes remain untested.
- Strict runtime: process alive after 12 seconds, zero fatal contexts/native
  crashes, session success observed, but pipeline compatibility false (exit 1).
  RAW still exhausts the HAL target-buffer list at 64 nodes / 60 consumers.
  The app was force-stopped and the phone returned to the launcher afterward.

Local evidence: `20261012-opencl-clean-photo-files.json`,
`20261012-opencl-clean-photo-decode.json`,
`20261012-opencl-clean-photo-logcat.txt`,
`20261012-opencl-clean-video-files.json`,
`20261012-opencl-clean-video-decode.json`, and
`20261012-opencl-clean-strict.json` under `device/marble/runtime`.

`scripts/patch_pixel_camera_opencl_guard.py` reproduces the tested native
library exactly from the verified input library SHA-256. It is a separate,
experimental command accepting source APK and new unsigned output APK paths;
align and sign the output using the existing build tools. It refuses different
library versions, modified instruction bytes, and fault-recorder APKs. The
wrapper's original unwind metadata is not regenerated or validated, so this
guard is not integrated into the release pipeline. Full camera functionality
remains unresolved because sustained RAW preview still fails.
